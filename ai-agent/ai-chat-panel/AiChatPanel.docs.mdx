# AI Chat

The AI chat panel: a header button that opens it, and a docked panel carrying the chat.

There is no `AiChatPanel` component to render. `useAiChatPanel` hands back the pieces and the
host decides where each one goes — the button belongs in the section's own header, the content
in a panel beside it.

### Features

- **Host-composed** — `chatButton` and `chatPanelContent`, plus the reactive visibility and fullscreen state
- **Section-agnostic** — reads only the shared `AiChatStore`, so every product surface mounts the identical panel
- **Docked or fullscreen** — `chatPanelWidth` is session state that resets on every open; fullscreen is set and unset explicitly, so the edge resizer can reach for either from a known state
- **Opt-out without a conditional hook** — `useAiChatPanel(false)` returns `undefined` for a section that does not offer AI

### Requirements

The tree has to sit inside `AiAgentProviders`, which mounts the `AiChatStoreProvider` the hook
needs; without it the hook throws. Consumers must be `observer`s, or the visibility and
fullscreen flags stop being reactive.

`@onlyoffice/ai-chat` is an **optional peer dependency** — importing anything under `ai-agent/`
without supplying it fails at build time naming the missing package.

**Whether AI is offered at all is the host's decision, not the trigger's.** `chatButton` only
hides itself once the panel is open; it does not consult availability. A host gates it on
`useIsAiChatAvailable()`, which returns `canUseAi && isAvailable` — whether the session may
reach AI at all (an anonymous or barred user: the providers still mount and descendants may
call `useStores()`, but hydration is skipped and no `/api/2.0/ai` request fires), and whether
this particular view offers it. Either one false withholds the trigger; both controls below
have to be on for it to appear.

The **surface is the host's**, not the panel's. `chatPanelContent` is a header and a chat body,
with no background and no outer edge of its own; in the DocSpace client it is rendered inside
`Section`'s info panel, which draws both from `--info-panel-background` and
`--info-panel-border-color`. A host that mounts the content in a bare container gets a chat
floating on the page with no boundary — the story below draws the same two so it does not.

### Default

<Story of={AiChatPanelStories.Default} />

```tsx
import { observer } from "mobx-react";

import AiAgentProviders from "@onlyoffice/apps-ui-kit/ai-agent/providers";
import { useAiChatPanel } from "@onlyoffice/apps-ui-kit/ai-agent/ai-chat-panel";

const Section = observer(() => {
  const {
    chatButton,
    chatPanelContent,
    isChatPanelVisible,
    isChatPanelFullscreen,
    chatPanelWidth,
  } = useAiChatPanel();

  return (
    <div style={{ display: "flex" }}>
      {!isChatPanelFullscreen ? <header>{chatButton}</header> : null}
      {isChatPanelVisible ? (
        <aside style={{ width: isChatPanelFullscreen ? "100%" : chatPanelWidth }}>
          {chatPanelContent}
        </aside>
      ) : null}
    </div>
  );
});

<AiAgentProviders locale="en">
  <Section />
</AiAgentProviders>;
```

### Not configured

The portal has no usable AI profile, so the panel opens on the branded not-available screen
instead of the composer. It takes both halves — `aiReady: false` **and** `noAccessProps`,
which is the wiring for the buttons on that screen; with only the first the body stays empty.

That is the point of the pair: a host that can route the user to portal AI settings (the
DocSpace client) passes `noAccessProps` and gets this screen, and a host that cannot (the
embedded sdk layouts) omits the chat props altogether and falls back to the chat widget's own
setup screen, which configures a profile in place.

### What renders in Storybook

The chat widget talks to `/api/2.0/ai` **on the page's own origin**, not through the `apiConfig`
portal switcher the selectors use. Served from a portal (`STORYBOOK_PROXY=1` behind nginx) that
origin is the portal and the chat reaches the real AI service.

In local Storybook the origin is the dev server, which has no such API — and an unanswered
init call is not a degraded chat but no chat at all: the widget's stores never finish
hydrating and the panel renders an empty `.aui-root`, with no composer and no setup screen.
So the dev server answers those routes itself, from `.storybook/ai-chat-mock.ts`: one mock
profile, threads and messages kept in memory for the life of the process, and a streamed reply
that echoes the prompt back. Nothing reaches a model. Set `STORYBOOK_AI_MOCK=0` to turn it off
and see the unanswered state.

`aiReady`, `canUseAi` and `isAvailable` are controls here, so the not-configured panel and a
session with no AI at all can both be reached without a portal either.
